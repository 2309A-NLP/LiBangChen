# RAG Q&A SYSTEM5 相对 RAG Q&A SYSTEM4 的优化说明

## 1. 文档目的

本文档用于说明 `RAG Q&A SYSTEM5` 相比 `RAG Q&A SYSTEM4` 的主要优化点，方便用于项目汇报、版本说明和阶段总结。

## 2. 对比口径说明

由于当前工作区中保留的是 `SYSTEM5` 的代码实现，而 `SYSTEM4` 主要可参考资料是验收文档 `docs/ACCEPTANCE_CHECKLIST.md`，因此本文档采用以下对比口径：

- 以 `SYSTEM4` 验收文档中体现的功能范围、待验证点、优化优先项作为“上一版基线”
- 以当前 `SYSTEM5` 的实际代码、配置、接口和测试覆盖作为“当前版事实依据”
- 对无法从现有材料直接证明的内容，不做绝对化表述，而使用“增强”“补强”“进一步完善”等表述

因此，这份文档是“基于现有仓库事实的版本优化总结”，适合作为项目说明文档使用。

## 3. 总体结论

相较于 `RAG Q&A SYSTEM4`，`RAG Q&A SYSTEM5` 的优化不只是界面或单点功能补丁，而是围绕以下几个方向做了系统性增强：

- 检索链路从单一检索思路，升级为“关键词检索 + 向量检索 + RRF 混合检索 + 可选重排”的可配置架构
- Query Understanding 从基础规则/在线理解，升级为支持本地优先、在线回退、多轮追问上下文改写的更完整理解链路
- 会话能力从“能保存历史”，增强为“历史可参与后续问题理解和回答生成”的多轮对话能力
- 系统可运维性增强，包括后台预热、预热状态跟踪、反馈持久化、Session 存储后端切换、Milvus 状态持久化等
- 工程化程度提升，包括依赖注入容器、模块拆分、更多测试覆盖、更多环境配置项

## 4. 主要优化点

### 4.1 多轮对话能力增强

这是 `SYSTEM5` 最明显、也最有业务价值的升级之一。

相较于 `SYSTEM4` 验收文档中“会话历史”主要作为功能点存在，`SYSTEM5` 在多轮对话上做了进一步增强：

- 支持 `session_id` 贯穿前后端
- 前端自动复用本地保存的 `session_id`
- 后端保存用户与助手历史消息
- 历史消息不只是展示，还会参与后续问答
- 对明显依赖上文的追问，新增“追问改写/上下文化”能力

这意味着 `SYSTEM5` 不再只是“记录聊天记录”，而是具备了更实用的多轮问答能力。像“那它的主营业务呢”“What about it?” 这类问题，系统会先结合历史把它改写得更适合检索，再进入理解和生成阶段。

### 4.2 Query Understanding 链路增强

`SYSTEM4` 的验收重点之一，是问题理解是否稳定、是否能做澄清、英文问答是否可用。`SYSTEM5` 在这条链路上做了更完整的补强：

- 支持 `rules`、`online`、`openai_compatible` 等多种理解模式
- 增加 `QUERY_UNDERSTANDING_LOCAL_FIRST_ENABLED`，简单问题可优先走本地规则，降低延迟和调用成本
- 增加 `QUERY_UNDERSTANDING_FALLBACK_ENABLED`，在线理解失败时可回退到本地规则，避免链路直接中断
- 支持歧义检测、澄清问题生成、子问题拆解、抽象目标提炼、检索提示生成
- 支持多轮追问上下文化改写，提升连续追问的理解质量

这部分优化的核心价值是：`SYSTEM5` 的问题理解更完整、更稳，也更适合真实业务场景中的模糊提问和连续提问。

### 4.3 检索架构升级

`SYSTEM4` 文档中已经把“先调检索，再调生成”列为优先事项。`SYSTEM5` 在检索层面明显做了架构化升级：

- 支持 `keyword` 关键词检索
- 支持 `milvus` 向量检索
- 支持 `hybrid_rrf` 混合检索
- 支持 `RRF_K` 等融合参数配置
- 支持可选 `reranker`

这带来的提升主要有三点：

- 对关键词明确的问题，保留高精度的词面召回能力
- 对语义表达变化较大的问题，补充向量召回能力
- 对复杂问题，通过混合召回和重排提高最终候选片段质量

从工程角度看，`SYSTEM5` 已经从“单一路径问答系统”升级为“可切换、可组合的检索框架”。

### 4.4 重排能力补强

`SYSTEM5` 新增了可配置的 Reranker 能力，用于对召回结果做二次排序：

- 支持 `RERANKER_ENABLED`
- 支持模型路径、运行设备、最大长度、TopN 等配置
- 初始化失败时可优雅降级，不会拖垮系统启动

这是一个典型的“效果层优化”。它不改变问答主流程，但能显著改善“正确片段召回了但排位靠后”的问题，对最终回答质量和引用质量都有帮助。

### 4.5 混合检索和向量库能力完善

相对 `SYSTEM4` 的验收阶段，`SYSTEM5` 已把 Milvus 相关能力工程化：

- 支持 Milvus 连接与集合管理
- 支持索引参数配置，如 `index_type`、`metric_type`、`nlist`、`nprobe`
- 支持 Milvus 状态持久化到 `data/processed/milvus_state.json`
- 支持启动后后台预热检索器

这说明 `SYSTEM5` 已经不只是“能接一个向量库”，而是把向量检索作为正式能力纳入了配置体系和生命周期管理中。

### 4.6 会话存储能力增强

`SYSTEM4` 中“会话历史”是验收点之一，而 `SYSTEM5` 在会话存储层继续增强：

- 支持内存 Session Store
- 支持 Redis Session Store
- Redis 不可用时自动回退到内存存储
- 支持 Session TTL 和 Key Prefix 配置

这一优化让系统从“开发演示可用”进一步迈向“多实例/可部署场景更友好”的状态。

### 4.7 后台预热与系统就绪性优化

`SYSTEM4` 验收范围里包含“检索预热与系统就绪状态”。`SYSTEM5` 在这方面已经形成更完整的机制：

- 启动时不阻塞首页访问
- 文档加载与检索预热放到后台线程
- 提供 `WarmupStatusService` 跟踪状态
- 提供 `GET /api/document/warmup` 接口
- 前端轮询预热状态并给出提示

这一点对实际体验很重要。相比“系统启动卡住”或者“首问特别慢但没有提示”，`SYSTEM5` 更适合给用户稳定、可解释的体验。

### 4.8 文档管理能力增强

`SYSTEM5` 继续完善了知识库管理能力：

- 支持多 PDF 上传
- 上传后自动解析并自动切换当前检索范围
- 支持文档列表查看
- 支持查看文档分块详情
- 支持删除文档后自动重建状态和重新预热

相较于“只有上传和提问”的轻量系统，这一版已经具备基础知识库运维能力，更适合持续迭代和真实测试。

### 4.9 本地抽取能力增强

`SYSTEM5` 在“检索之后、生成之前”增加了本地精确抽取逻辑，用于特定问题直接从片段中抽答案，而不是所有问题都依赖 LLM 生成。

当前覆盖的典型场景包括：

- 获奖工程类问题
- 技术标准类问题
- 财务指标/表格类问题

这一优化的价值在于：

- 降低对 LLM 的依赖
- 提高结构化问题的准确率
- 对财务表格类问题更稳定
- 减少幻觉风险

这正好对应了 `SYSTEM4` 验收文档中提到的“财务表格问题稳定性”这一重点。

### 4.10 引用质量增强

`SYSTEM4` 已把“引用质量”列为核心验收项。`SYSTEM5` 在引用组织方式上更细致：

- 引用包含文档名、页码、评分
- 为引用构建更聚焦的摘要片段
- 财务场景优先匹配表格行
- 通用场景优先截取焦点词附近窗口

这比简单返回整段 chunk 更利于用户核对答案来源，也更适合做人工验收。

### 4.11 反馈闭环增强

`SYSTEM5` 已把用户反馈纳入正式能力：

- 提供 `POST /api/feedback`
- 反馈以持久化文件方式保存
- 支持答案 ID、评分、评论等结构化信息

这意味着系统已经具备最基础的“效果闭环”能力，后续可以据此做错误样本积累、问答集构建、RAG 评估和持续优化。

### 4.12 配置能力显著增强

`SYSTEM5` 的 `.env` 配置项明显比早期系统更完整，已经覆盖：

- LLM 配置
- Query Understanding 配置
- 检索器类型配置
- Reranker 配置
- Embedding 配置
- Milvus 配置
- Session Store 配置
- 路径与持久化配置

这说明 `SYSTEM5` 已经从“代码里写死逻辑”走向“通过配置组合能力”的阶段，后续维护、实验和部署都会更方便。

### 4.13 工程结构优化

`SYSTEM5` 在代码组织上也更成熟：

- 引入 `AppContainer` 做依赖注入与统一装配
- 服务按职责拆分为 ingestion、query_understanding、retrieval_generation、pipeline、feedback、session、warmup 等模块
- retriever、llm、session store 都采用工厂/抽象层设计
- 保留 mock 实现，方便开发与测试

这一类优化不一定直接体现在界面上，但对后续版本演进非常关键，能明显降低继续迭代的成本。

### 4.14 测试覆盖增强

从仓库现状看，`SYSTEM5` 已有较完整的测试拆分，包括：

- API 路由测试
- Query Understanding 测试
- LLM 集成测试
- 检索与生成测试
- 文档解析测试
- Embedding 测试

这比“只有手工验收”更进一步，说明 `SYSTEM5` 已经具备基本的自动化验证能力。

## 5. 从 SYSTEM4 待优化项到 SYSTEM5 落地结果的对应关系

结合 `SYSTEM4` 验收文档中的优化优先级，可以把 `SYSTEM5` 的提升概括为以下映射：

### 5.1 对 P0 / P1 重点问题的响应

`SYSTEM4` 文档中强调的重点包括：

- 先优化检索，再优化生成
- 财务表格问题稳定性
- 英文问答效果
- 澄清逻辑稳定性
- 首问延迟与预热体验

`SYSTEM5` 对应落地如下：

- 通过 `keyword + milvus + hybrid_rrf + reranker` 明显加强检索层
- 通过本地表格抽取增强财务类问题稳定性
- 通过语言识别、英文系统提示词、在线理解链路补强英文问答
- 通过歧义检测、澄清问题、多轮改写提升澄清和追问能力
- 通过后台预热和 warmup 状态跟踪改善首问体验

### 5.2 对“真实可用性”的响应

`SYSTEM4` 中很多内容仍然偏验收视角，而 `SYSTEM5` 更偏“可连续运行的系统视角”：

- 支持 Redis 会话存储
- 支持反馈沉淀
- 支持向量检索落地
- 支持文档管理页
- 支持后台预热状态
- 支持更多配置切换

这说明 `SYSTEM5` 已经不只是“演示一个 RAG 问答流程”，而是更接近一个可持续调试、可运维、可扩展的问答系统。

## 6. 可以对外简述的版本总结

如果要用一句话概括，可以这样表述：

> RAG Q&A SYSTEM5 在 SYSTEM4 的基础上，完成了从“基础 PDF 问答系统”向“具备混合检索、多轮对话、上下文理解、可配置部署与可运维能力的增强版 RAG 系统”的升级。

如果要用更业务化的表达，可以这样写：

> 相比 SYSTEM4，SYSTEM5 的核心提升在于：问得更懂、检得更准、答得更稳、会话更连续、系统更易维护。

## 7. 当前仍可继续优化的方向

虽然 `SYSTEM5` 已经明显强于 `SYSTEM4`，但从当前代码状态看，后续仍可继续增强：

- 进一步把本地追问改写从“保守拼接”升级为“更自然的实体补全”
- 持续清理部分历史文档中的命名和编码遗留问题
- 补充更系统的真实业务题库与评测集
- 加强英文语料下的检索提示和关键词扩展能力
- 增加 OCR 能力，覆盖扫描版 PDF

## 8. 结论

`RAG Q&A SYSTEM5` 相比 `SYSTEM4` 的提升，主要不是单个功能点新增，而是完成了以下几类关键升级：

- 从单轮问答走向基础多轮对话
- 从单一检索走向混合检索与可选重排
- 从基础问题理解走向本地优先、在线回退、追问上下文化
- 从功能可用走向更可配置、更可运维、更可测试

因此，如果用于项目汇报，完全可以将 `SYSTEM5` 定义为 `SYSTEM4` 的“能力增强版”和“工程化升级版”。
